# 智慧校园办事与入学助手 —— 初版 App 方案

面向 Light，按已锁定方向整理，可直接作为初版开发依据。不绑定尚未公布的第十六届软件杯赛题，也不绑定金蝶苍穹。目标是先做出能给师生真正用起来的产品初版。

---

## 1. 产品概述与原则

### 1.1 一句话定位

这是一款**师生共用的校园办事与入学助手**。核心目的是帮学生少花时间：该知道的一次问清、该填的少填、该办的按步骤办完。

它**不是**教务系统，也**不是**第二套学习通。成绩录入、排课、正式学籍库仍以学校已有系统为准；本 App 负责把规章讲清楚、把手续跑完整、把待办收拢到一处。

### 1.2 对外怎么用

学生和老师面对的是**一个总管智能体**（首页那句提问）。总管只做四件事：理解意图、把缺的信息补全、把任务分给内部智能体、把结果汇总成可读答复和可点的下一步。知识回答、规则校验、单据生成分别由三个下辖智能体完成，用户不必感知这些分工。

学生有两种使用模式，**同一套知识库，按身份过滤**：

- **新生模式**：偏引导。入学清单、报到步骤、校园百科（宿舍、网费、班车、常见地点等）。
- **全年级模式**：偏办事。请假、补证、奖助预审、作业与志愿者等待办。

老师可发布任务、作业、志愿者招募，并审批请假等事务。

### 1.3 必须遵守的原则

1. **少填、少跑、少猜。** 个人档案只填一次，之后能预填的一律预填；能在确认页一次看清的，不要拆成多轮追问。
2. **有依据才回答。** 知识问答必须带出处。知识库没有就明确说没有，不编造，并给出人工入口。
3. **有校验才出单。** 请假条、证明申请、奖助草稿等，必须先经规则校验，通过后才能生成单据。
4. **系统不代替拍板。** 关键事务：学生在确认页亲自确认，老师审批。系统只建议、预审、提醒，不擅自提交、不擅自批准。
5. **按身份可见。** 无权限查看的规定，只提示「需辅导员查看」，不打码、不泄露正文。
6. **首页极简。** 只看待办和一句提问。老师发布的作业和招募也进入同一条待办流。

## 2. 角色与权限

初版只做三种前台角色。管理员不进 App 日常界面，只在后台导入规章和名单，比赛与联调用演示数据即可。

| 角色 | 谁来当 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **学生** | 新生与在校生（按年级自动切换模式侧重） | 提问、查看本人待办与提醒、维护档案、发起/确认请假与销假、查看奖助预审提醒并生成申请草稿、报名志愿者、查看并完成报到/作业任务、复用有效期内材料 | 看不到无权限规章正文；不能改他人档案；不能跳过确认页提交；不能自己批准自己的假 |
| **任课教师** | 授课老师 | 发布/收回作业任务、查看本课提交与完成情况、在「影响本课考试/课堂」的请假中参与审批（按规则触发时）、提问公共知识 | 不能审批纯事务类短假（归辅导员）；不能查看与本课无关的学生敏感档案；不能发布全校级行政通知（初版不做） |
| **辅导员 / 班主任** | 年级辅导员或班主任 | 审批本班/本年级请假、查看学生办事进度、对学生无权限阅读的规定给出人工说明、发布本班任务、查看奖助预审名单（结果与匹配理由，非自动提交）、提醒催办 | 不能代替学生提交申请；不能在系统里直接改成绩或困难认定结论（这些来自授权数据源，变更后由系统重算） |

**管理员（仅后台）：** 导入/更新规章文件与生效学期、导入学生和教师名单与班级归属、配置审批规则（如短假/跨天阈值）、配置知识库可见范围、管理演示数据。不参与日常问答与审批。

**身份过滤规则（知识库）：**

- 每条知识切片标注可见角色与适用对象（如「全体学生」「新生」「辅导员内部」）。
- 学生检索时自动加上本人年级、学院、身份（新生/在校生）。
- 命中「仅辅导员」的条目：对学生只返回固定提示「该规定需辅导员查看」，并给出「转给辅导员」入口，**不返回正文、不打码预览**。

**数据权限：** 学生只看本人；任课教师看本课程相关任务与被规则点名的请假；辅导员看所带班级/年级。敏感档案字段默认不展示，须学生按需授权后，才在对应办事流程中使用。

## 3. 信息架构与主要页面

整体是「一问 + 待办」为主，办事表单都从对话或待办钻进去，不做成功能仓库式首页。

### 3.1 信息架构

```
启动 / 登录
 └─ 身份：学生 | 任课教师 | 辅导员
      └─ 首页（待办列表 + 一句提问）
           ├─ 待办详情（作业 / 报到 / 招募 / 请假销假 / 奖助提醒 / 证明草稿）
           ├─ 对话结果页（结论 / 依据 / 去办理）
           │    └─ 依据卡片 → 原文高亮
           ├─ 办事确认页（提交前必经）
           ├─ 我的档案
           ├─ 提醒中心（可按类关闭）
           └─ 我的申请与材料（历史单据、可复用附件）

教师 / 辅导员另有：
 ├─ 发布（作业 / 志愿者招募 / 报到或班级任务）
 ├─ 审批箱（请假等）
 └─ 进度名单（本课或本班）

后台（Web，管理员）：
 规章库、名单导入、角色与可见范围、审批规则、演示数据
```

### 3.2 学生首页（初版唯一主界面）

只保留两块：

1. **一句提问：** 输入框，可打字，也可上传假条/病例等照片作为提问附件。例如「明天上午去医院，怎么请假」「国家励志奖学金我能申请吗」。
2. **待办列表：** 按截止时间排序。类型包括：待确认的请假、待销假、奖助预审提醒、报到任务、老师布置的作业、志愿者招募、被拦住待补件的申请。每条待办显示标题、截止/时效、一个主按钮（去办理 / 去确认 / 去销假）。

没有「九宫格功能入口」。要办事，问一句或点待办即可。

新生登录后，待办顶部固定「入学与报到」分组，未完成的报到项排在前面；进入在校学期后，该分组自动收起，未完成项仍留在待办里。

### 3.3 其他必要页面（都能从首页到达）

| 页面 | 用途 | 要点 |
|---|---|---|
| **对话结果页** | 展示总管汇总后的回答 | 固定三块：结论、依据、去办理/生成草稿。见第 5 节。 |
| **原文阅读** | 从依据卡片或句末角标进入 | 打开源文件对应条款/章节，高亮引用片段，展示文件名、条款、生效学期。 |
| **确认页** | 任何提交前的最后一步 | 展示将要提交的全部字段、预填来源、时长/审批人/依据/附件；必须学生点「确认提交」。 |
| **我的档案** | 只填一次，可随时改基础项 | 基础字段直接维护；敏感项默认收起，按事项单独授权。 |
| **提醒中心** | 时限、资格、异常三类 | 每条带引用和办理按钮；同类合并；可关闭某一类提醒。 |
| **我的申请与材料** | 历史请假、证明、奖助草稿、已上传附件 | 标注有效期，有效期内可一键复用。 |
| **教师：发布** | 作业、志愿者招募、报到/班级任务 | 标题、说明、截止时间、对象范围（课程/班级）、是否需要提交物或报名表。发布后进入对应学生待办。 |
| **审批箱** | 辅导员/教师处理请假等 | 列表 + 详情：申请摘要、时长、依据、附件、校验结果。操作：批准 / 退回（必填原因） / 转交（规则允许时）。 |

初版不做独立「消息 tab」：通知全部进入待办或提醒；系统回复仍在对话结果页查看。

## 4. 个人档案与可预填表单

### 4.1 基础字段（只填一次，默认用于预填）

| 分组 | 字段 |
|---|---|
| 身份 | 学号、姓名 |
| 在读信息 | 学院、专业、年级、班级 |
| 联系 | 手机、邮箱 |
| 日常 | 辅导员、宿舍、床位 |
| 紧急联系人 | 姓名、关系、电话 |

以上变更由学生在「我的档案」自行更新；学号、姓名、学院专业年级班级在初版可由管理员导入，学生申请更正，避免与名单冲突。

### 4.2 敏感项（默认不预填，按需授权）

银行卡、家庭经济情况、成绩、困难认定结果等。授权原则：

- 按**这一次办事**授权，界面写清「将用于：××申请」，不要一次勾成永久全开放。
- 授权范围写入申请记录，便于审计。
- 未授权时，对应预审或预填直接跳过该字段，并在确认页标明「未授权，未使用」。
- 奖助预审若缺少必要授权，不编造资格，只提醒「完成××授权后可重新预审」。

### 4.3 可预填的办事（初版）

| 事项 | 从档案预填 | 学生本次只需补的 |
|---|---|---|
| 请假 / 销假 | 学号姓名、学院班级、辅导员、联系方式 | 时间、原因、去向、附件（假条/病例等）；销假时确认返校时间 |
| 补办学生证 / 开具证明 | 学号姓名、学院专业年级、照片或证号（若已有） | 补办原因、领取方式；证明用途与份数 |
| 志愿者报名 | 学号姓名、学院班级、手机 | 可参加时段、已有志愿经历（可选） |
| 奖助申请草稿 | 已授权的成绩、困难认定、银行卡等 | 个人陈述、本次上传材料；确认匹配到的项目后生成草稿 |

**提交前必须经过确认页。** 确认页需要展示：预填了哪些字段、哪些是本次手填、附件清单、将送给哪位审批人、所依据的条款、提交后不可擅自撤回的说明（撤回规则初版：审批前可撤回，审批中需联系审批人退回）。

## 5. 知识引用与智能提醒

### 5.1 知识回答的固定结构

每一条知识类回答，界面固定三块，缺一不可：

1. **结论：** 用短句直接回答「能办吗 / 怎么做 / 要注意什么」。
2. **依据：** 一组引用卡片，不是一段无出处的说明。
3. **去办理 / 生成草稿：** 若该结论对应可办事事项，给出主按钮（去请假、生成奖助草稿、去报名等）；若仅是查阅，则提供「转人工 / 问辅导员」入口，不硬造办理按钮。

**引用卡片必备信息：** 文件名、条款或章节、生效学期。点击卡片进入原文阅读，并高亮被引用片段。

**句级角标：** 结论里关键句可加角标，点击同样跳到对应原文位置。多文件并列展示，不合并成一条糊涂出处。

**冲突处理：** 两份文件或两个学期规定不一致时，必须写明「以《××》××学年春季学期第×条为准」，并同时列出被搁置的另一份，避免学生只看到一面之词。冲突裁决规则初版采用：同文件以较新生效学期为准；不同文件以管理员在后台标记的「优先文件」为准；都未标记则提示人工确认，不擅自选择。

**没有依据：** 明确说「知识库中没有找到相关规定」，禁止补写看似合理的内容；同时给出人工入口（转辅导员或学校办事窗口联系方式，由后台配置）。

**无权限：** 只提示需辅导员查看，提供转办，不打码漏出正文。

### 5.2 知识库怎么支撑上述展示（初版就要按此入库）

后台导入 PDF / Word / 纯文本时，管理员填写：文件名、生效学期、适用角色、适用学院或全体、是否优先文件。入库后按条款/章节切块，每块保留原文、锚点（页码或条款号），供检索和原文高亮。初版允许先半自动切块、管理员校对，不要求一次做成全自动完美抽取。

### 5.3 智能提醒：三类

| 类型 | 何时产生 | 提醒里必须有 |
|---|---|---|
| **时限** | 请假将到期未销假、报到或作业临近截止、材料即将过期 | 引用（若涉及规章时限）+ 办理按钮（去销假 / 去提交） |
| **资格** | 奖助预审由「不够格」变为「可能符合」，或证明/补证满足条件 | 匹配理由 + 条款引用 + 去查看草稿（**不自动提交**） |
| **异常** | 材料缺失、审批被退回、成绩或认定变更导致原预审失效、过期项目被撤下 | 缺什么或为何失效 + 办理或查看按钮 |

**合并与关闭：** 同一类、同一事项的多条提醒合并为一条（例如同一门课的作业截止，不连发三条）。学生可在提醒中心关闭「时限 / 资格 / 异常」中的某一类；关闭后不再推该类，但对应待办仍保留，以免漏办。辅导员侧不提供关闭「本班异常」以免漏管，初版可只对学生开放关闭。

提醒入口：首页待办中插入高优先级项，同时在提醒中心可回顾。

## 6. 请假与奖助流程

### 6.1 请假闭环（初版要尽可能方便）

**发起（两种入口，效果相同）：**

- 一句话，如「周三下午去医院」。
- 或直接拍假条 / 病例照片上传。总管识别时间、原因、材料类型；认不准的字段在补全环节问一次，不要连问五六轮。

**系统自动做的事：**

- 用档案预填学号、姓名、学院班级、辅导员、联系方式。
- 根据话术或照片解析出起止时间，计算时长，判断是否跨天、是否与已发布的考试/课堂任务冲突（考试与课堂数据初版来自：教师已发布的作业/考试任务 + 管理员导入的考试安排表；没有数据则不强行判断，只提示「未发现冲突记录，请自行确认」）。
- 走校验智能体：必填是否齐全、时长是否合理、附件类型是否满足该假种要求、审批链该走哪一级。

**材料不全：当场拦住。** 明确列出缺什么（例如「跨天病假需要病例或诊断证明，当前只有文字说明」），给学生「去拍照补充」或「改时间后重试」，不生成可提交单据。

**确认页必须展示：** 请假时长、起止时间、原因、预填信息、附件、审批人（及加签层级说明）、所依据的请假条款、提交后的效力说明。

**审批层级（初版规则，可在后台改阈值）：**

- **短假且不影响已登记考试：** 辅导员/班主任审批即可。默认「短假」= 不超过 1 个自然日且不跨天（后台可调）。
- **跨天，或与已登记考试/课堂冲突：** 在辅导员审批之外加一层。冲突本课考试时加签任课教师；无课表冲突但跨天时，加签规则初版为「辅导员审批 + 年级负责人（若名单中有；没有则辅导员审批并备案）」——若演示数据没有年级负责人，界面写清「本演示环境由辅导员终审并备案」。

**批准之后：**

- 写入学生待办：请假已生效的说明 + 到期销假提醒（时限类）。
- 写入辅导员/相关教师的进度视图。
- 学生返校后一句话或点待办即可销假；销假同样走确认页，默认预填返校日为假期结束日。

**材料复用：** 假条、病例等附件标注有效期（由校验规则给出，如该病例证明上的日期起 N 天，初版缺日期则默认 7 天并允许辅导员调整）。有效期内再次请假可一键带入，仍须走确认页。过期材料不可选，或选中后当场提示已过期。

**撤回与驳回：** 审批前学生可撤回；驳回后待办出现「异常」项，展示退回原因，可改完再提交。

### 6.2 奖助（及同类证明）预审

奖助在初版定位是**资格预审 + 主动提醒 + 草稿**，不是自动报名器。

**流程：**

1. 管理员入库奖助文件（条件、材料清单、开放学期与截止日）。
2. 学生授权必要敏感项后，校验智能体按条款做匹配。
3. **可能符合：** 产生「资格」类提醒，内容包括匹配理由（哪几条符合）+ 条款引用 +「查看并生成草稿」。**不自动提交。**
4. **不够格：** 不推送资格提醒。学生主动来问时，可以在结论中说明暂不符合及依据，并列出缺的条件（如成绩未达、未完成困难认定授权），不鼓励反复打扰。
5. 学生点进去后，预填已授权字段，补个人陈述和材料，经校验通过，进入确认页，再提交给学校既有流程或初版内的「草稿已生成，请按学校通道报送」（若初版暂无对接校级奖助系统，确认后状态为「草稿已确认，待学生按指引报送」，并把材料包打包下载）。方案允许初版先做到「确认后的标准申请包」，不阻塞在尚无的校方接口上。
6. **重算与撤下：** 成绩、困难认定、档案或授权变更后重新计算。由符合变为不符合，或项目过期：撤下资格提醒，已有未提交草稿标记为失效并说明原因；已确认待报送的草稿发出异常提醒，由学生决定作废或补充。

**证明 / 补办学生证**按同一套「预审 → 补件拦住 → 确认页 → 提交/生成办理包」处理，审批人按后台规则（多为辅导员或学工窗口，初版用辅导员）。

## 7. 其余四件初版事项怎么落地

知识问答、请假、奖助预审已在上文展开。另外三件同样进同一待办，不再另做一套首页。

### 7.1 报到任务（新生为主）

- 管理员或辅导员按「入学批次」发布报到清单（如：填写档案基础字段、上传证件照、确认宿舍床位、完成指定入学教育阅读、到校签到等）。
- 每项是一条待办，可勾选完成或提交凭证。依赖项要写清（例如先填档案再确认宿舍）。
- 清单说明若引用入学须知，待办详情里带依据卡片。
- 到截止日期仍未完成：时限提醒；关键项未完成可在辅导员进度名单中标红。

### 7.2 作业任务（任课教师发布）

- 教师填写标题、说明、截止时间、提交方式（无需提交 / 上传文件 / 仅确认已完成）、对象为所授课程名单。
- 发布后进入该课学生待办；临近截止发时限提醒。
- 教师可看完成名单。初版不做自动批改、讨论区和复杂评分，避免做成学习通。

### 7.3 志愿者招募（教师或辅导员发布）

- 发布：活动名称、时间地点、名额、条件、报名截止、是否需要审核。
- 进入对象学生待办；报名表预填档案，学生只补时段等当场信息，确认后提交。
- 若有条件（如年级、是否已完成某培训），先校验再报名；不符合则当场说明依据，不让提交。
- 需要审核时，发布人在审批箱处理；通过后给学生一条确认待办（活动前提醒到场）。

## 8. 智能体分工

用户只面对总管。内部三个下辖智能体分工固定，初版就必须按此拆开实现，避免做成「一个大模型包办」。

| 智能体 | 职责 | 明确不做 |
|---|---|---|
| **总管** | 理解意图；发现缺信息时做最少次数的补全；把任务分给知识 / 校验 / 办事；汇总成「结论 + 依据 + 去办理」或确认页数据；控制对话不跑题 | 不直接引用规章原文做最终答复；不直接判定资格或生成单据；不替学生确认、不替老师批准 |
| **知识** | 只在权限范围内检索知识库；返回带锚点的依据片段、冲突说明、无结果标记；为提醒和结论提供引用 | 不编造条款；不回答无检索支撑的规定；不把无权限正文发给总管用于展示 |
| **校验** | 按规则检查资格、材料完整性、假种与时长、审批层级、冲突、授权是否足够；输出通过 / 拦住及「缺什么」；奖助匹配理由；材料有效期 | 不做自然语言闲聊；不生成对外文书；不因「看起来合理」而放行 |
| **办事** | 在校验通过后生成单据或草稿、预填档案、写入待办与提醒、推进状态机（已提交 / 审批中 / 已批准 / 待销假 / 已驳回等） | 校验未通过时不出单；不自动提交奖助；不自动审批 |

**一次典型请假的内部顺序：** 总管识别「请假」并补全时间原因 → 办事预填档案草稿 → 校验检查材料与层级 → 不通过则总管当场说明缺件；通过则总管出示确认页 → 学生确认后，办事提交并通知审批人。全程知识智能体为确认页和提醒提供条款引用。

**一次知识问答：** 总管判断是查阅还是要办事 → 知识检索并组织依据 → 若可办事，总管在第三块给出入口，真正出单仍走校验 + 确认。

所有智能体日志保留：检索到的文档 ID、校验规则 ID、是否出单，便于演示时说明「不是黑盒一句生成」。

## 9. 初版范围与二期

### 9.1 初版锁定只做这 6 件事

1. 带出处的知识问答（结论 / 依据 / 去办理，原文高亮，冲突写明，无依据不编造，无权限不漏文）
2. 请假闭环（一句话或拍照发起，预填，当场拦缺件，确认页，短假/跨天分层审批，待办与销假，材料复用）
3. 奖助或证明预审（匹配才提醒，不自动提交，不够格不推，变更重算，过期撤下）
4. 报到任务
5. 作业任务
6. 志愿者招募

加上支撑这 6 件事的：三种角色与权限、个人档案与按需授权、智能提醒（时限 / 资格 / 异常）、首页待办 + 一句提问、后台规章与名单导入、演示数据。

### 9.2 初版明确不做

报修、选课、课表对抗式冲突的完整教务对接、成绩录入与自动批改、社交/论坛、支付与网费充值、把 App 做成第二教学平台。老师「发布」只服务作业、招募、报到/班级任务，不做校园信息流运营。

### 9.3 二期（先记下来，不进初版排期）

报修、选课意向或选课指引、与教务/学工/奖助正式系统的对接、统一身份登录、更细的审批流与会签、多校区百科、数据看板。等第十六届赛题公布后，用初版能力去适配赛题，而不是等赛题再开始做产品。

## 10. 实现建议（务实默认）

下面给一套能按时做出初版的默认技术选型。若团队更熟其他等价栈，可以替换，但不要在初版同时试两条路线。

### 10.1 技术栈

| 层级 | 默认选择 | 原因 |
|---|---|---|
| 学生/教师端 | **Flutter**，同时出 Android 与 iOS App | 一套代码覆盖提问、待办、拍照上传；答辩可直接装 App。微信小程序初版不做，需要时再另补，不要求 Flutter 直接出小程序 |
| 管理后台 | **Vue 3 + Vite + Element Plus** | 规章入库、名单导入、规则配置足够 |
| 后端 API 与智能体编排 | **Python FastAPI** | 与模型、检索、校验规则放在一起最省事 |
| 数据库 | **PostgreSQL**（含 **pgvector**） | 业务表 + 向量检索一库搞定，演示部署简单 |
| 缓存与队列 | **Redis** + 轻量任务队列（如 ARQ / Redis 队列） | 提醒重算、入库切块不要堵在请求里 |
| 文件 | 本地对象存储或 **MinIO**（演示），预留 OSS | 假条、病例、证明扫描件 |
| 大模型 | 可替换的国内 API（如 DeepSeek / 通义），配置放环境变量 | 总管的理解与汇总、拍照字段抽取；**知识正文不得靠模型记忆** |
| 智能体实现 | 三个内部智能体做成明确服务/模块（知识检索、规则引擎、办事状态机），总管用编排调用 | 校验建议「规则引擎为主、模型为辅」：条件、时限、缺件用结构化规则，模型只负责抽取和说明 |
| 认证 | 初版：账号 + 角色（演示名单导入）；接口预留统一身份 | 不阻塞开发 |
| 部署 | **阿里云 ECS**（华南 3 / 广州，4 核 8 GB，Ubuntu 22.04，公网 IP `8.148.186.220`）+ **Docker Compose** 拉起 API、数据库、MinIO、后台 | 初版演示和小范围试用足够。系统盘 40 GB 偏紧，建议另挂 50–100 GB 数据盘存放数据库与附件，并开启备份。当前为按量付费、按使用流量计费，长期运行可再考虑包年包月 |

移动端与后端之间走 HTTPS JSON API。所有「生成草稿 / 提交 / 审批」必须走服务端校验，不能只信模型或只信前端。 Flutter 端负责界面、拍照和调用接口，可使用常见的网络与状态管理方案（如 Dio、Riverpod 或 Provider）；档案、规章、待办、附件以及大模型检索与调用一律放在云端服务端，学生端不落业务库、不下发模型或规章全文。发布安装包控制在 1 GB 以内（目标为常规几十 MB 级）；本地最多保留缩略图或可清理缓存。首次使用需联网；离线最多查看已缓存待办，不允许在无网时由模型作答。知识正文以服务端检索为准，不得依靠模型记忆条款。模型调用、规则校验和审批状态一律走服务端，不要写进 App。

### 10.2 关键实现要点

- **端云分工：** 学生端不落业务库；数据与模型调用都在云端；安装包控制在 1 GB 以内。
- **引用可追溯：** 每条依据存 `document_id + chunk_id + 条款/章节 + 生效学期 + 原文偏移`，原文高亮才做得到。回答里禁止出现没有 ID 的「据说」。
- **规则配置化：** 短假阈值、加签条件、奖助条件、材料有效期放后台或规则表，不要写死在提示词里。
- **状态机：** 请假、报名、奖助草稿用显式状态（草稿 / 待确认 / 已提交 / 审批中 / 已批准 / 待销假 / 已驳回 / 已撤回 / 已失效），便于待办和提醒生成。
- **重算：** 档案、成绩授权、认定结果、规章生效学期变更时，重跑奖助匹配和相关提醒，过期或失效要撤下。
- **照片发起请假：** 初版用模型抽取时间、医院/事由、证件类型，抽取结果必须让学生在补全或确认页改，不能直接当已校验材料。
- **日志：** 保留检索、校验、出单记录，演示「有依据、有校验、有确认」。
- **隐私：** 敏感字段加密存储，按事项授权，日志中不写银行卡号等明文。

### 10.3 建议的实现顺序

1. 后台：名单与规章入库、原文切块与引用锚点、三种角色登录。
2. 档案 + 首页（提问框 + 待办框架）+ 知识问答三块展示和原文高亮。
3. 请假全闭环（含拍照抽取、校验拦住、确认页、审批、销假、材料复用）。
4. 奖助预审提醒与草稿（含重算和撤下）。
5. 报到、作业、志愿者三条任务流接入同一待办。
6. 提醒三类、合并与关闭；用演示数据把新生/在校生、教师、辅导员三条路径跑通。

### 10.4 演示数据（初版就准备，不必等赛题）

准备一个班级的学生（含新生与高年级）、一名辅导员、两名任课教师；若干份带学期的规章（请假规定、奖助办法、入学须知，其中安排一处「新旧学期冲突」用于展示裁决）；若干作业、一场招募、一份报到清单；一两个奖助项目（有人符合、有人不符合）。足以演示六件事，无需接真实教务。

## 11. 初版验收标准（便于对照开发）

做到以下几点，即可视为初版可用：

- 学生打开 App，首页只有待办和一句提问；作业与招募出现在同一待办中。
- 问规章时，答复固定为结论、依据、去办理；依据可点到原文高亮；冲突会写明以哪份哪个学期为准；库中没有时不编造并给出人工入口；无权限规定不漏正文。
- 档案只维护一份；请假/补证/志愿者/奖助草稿能预填；提交前必经确认页。
- 一句话或一张假条照片能发起请假；缺材料会被当场拦住并说明缺什么；短假与跨天/影响考试走不同审批；批准后出现销假待办与时限提醒；有效材料可复用。
- 奖助只在可能符合时提醒，提醒含理由和条款，不自动提交；不够格不推；条件变化或过期会重算并撤下。
- 总管只做理解、补全、分流、汇总；知识、校验、办事职责不混用；系统不代替学生确认或老师审批。
